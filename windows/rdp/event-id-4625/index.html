    RDP ошибка 0x4 при рабочем порте 3389. Диагностика Schannel 36870 и Event ID 1057

    Windows Server • RDP • Terminal Services • TLS • Schannel

    о проблеме

    На одном из клиентских ПК под Windows 10 перестал работать RDP.

    Клиент при подключении получал сообщение:

    Произошла внутренняя ошибка.

Код ошибки: 0x4
Расширенный код ошибки: 0x0

    При этом порт TCP/3389 продолжал отвечать, а служба удаленных рабочих столов выглядела полностью работоспособной.

    На первый взгляд проблема напоминала типичную неисправность службы RDP или сетевого подключения, однако дальнейшая диагностика показала совершенно другую причину.

    В статье показан полный порядок диагностики и решение, которое позволило восстановить работу сервера.

    симптомы

    На момент начала диагностики наблюдалось следующее.

    ✔ клиент получает ошибку 0x4

    ✔ порт TCP/3389 доступен

    ✔ служба TermService запущена

    ✔ слушатель RDP-Tcp находится в состоянии «Прием»

    ✘ подключение по RDP не выполняется

    что было известно

    Проверка через qwinsta показала, что слушатель RDP работает.

    qwinsta

    Результат:

     СЕАНС             ПОЛЬЗОВАТЕЛЬ             ID  СТАТУС
 services                                    0  Диск
 console           USER                      1  Активно
 rdp-tcp                                 65536  Прием

    Также было известно:

    • служба TermService запущена;
    • порт TCP/3389 доступен;
    • TCP-соединение устанавливается;
    • telnet до порта 3389 выполняется успешно;
    • слушатель RDP находится в состоянии «Прием».

    Note

    На данном этапе проблема уже не выглядела как неисправность сети, брандмауэра или самой службы удаленных рабочих столов.

    01. проверяем журналы terminal services

    Первым шагом проверяем журналы служб удаленных рабочих столов.

    Get-WinEvent `
    -LogName "Microsoft-Windows-TerminalServices-RemoteConnectionManager/Operational" `
    -MaxEvents 50 |
Select TimeCreated, Id, Message

    Дополнительно проверяем журнал локального диспетчера сеансов.

    Get-WinEvent `
    -LogName "Microsoft-Windows-TerminalServices-LocalSessionManager/Operational" `
    -MaxEvents 50 |
Select TimeCreated, Id, Message

    Проверка показала, что служба продолжает принимать подключения.

    Кроме того, в журнале присутствовали события успешного входа пользователей.

    Это означало, что проблема находится не на уровне TCP и не на уровне самого слушателя RDP.

    02. проверяем системные ошибки

    Следующий шаг - анализ системного журнала.

    Get-WinEvent `
    -FilterHashtable @{
        LogName='System'
        StartTime=(Get-Date).AddMinutes(-10)
    } |
Select TimeCreated, ProviderName, Id, LevelDisplayName, Message |
Format-List

    Практически сразу были обнаружены повторяющиеся ошибки Schannel.

    Event ID: 36870

Произошла неустранимая ошибка при попытке обращения
к закрытому ключу учетных данных TLS server.

Код ошибки:
0x8009030D

    Одновременно фиксировались ошибки службы удаленных рабочих столов.

    Event ID: 1057

Серверу узла сеансов удаленных рабочих столов
не удалось создать новый самозаверяющий сертификат
для использования при проверке подлинности сервера.

Код состояния:
Указан неправильный алгоритм.

    Warning

    Уже на этом этапе стало понятно, что диагностику необходимо продолжать в сторону TLS, сертификатов и криптографической подсистемы Windows.

    03. проверяем состояние служб

    Проверяем службы, участвующие в работе TLS и криптографии.

    Get-Service `
    TermService,
    KeyIso,
    CryptSvc |
Format-Table Name, Status, StartType -Auto

    Результат:

    TermService Running
KeyIso      Running
CryptSvc    Running

    Все необходимые службы были запущены и работали без ошибок.

    04. проверяем сертификаты

    Проверяем сертификаты локального компьютера.

    certutil -store My

    После этого проверяем специализированное хранилище сертификатов Remote Desktop.

    certutil -store RemoteDesktop

    Результат оказался неожиданным.

    CertUtil: -store команда НЕ ВЫПОЛНЕНА

0x80070002

Не удается найти указанный файл.

    Хранилище сертификатов Remote Desktop отсутствовало.

    На этом этапе стало понятно, что проблема связана не только с самой службой удаленных рабочих столов, но и с инфраструктурой сертификатов Windows.

    05. дополнительная диагностика

    Во время проверки криптографической подсистемы внимание привлекло неожиданное поведение certutil.

    Для просмотра установленных криптопровайдеров была выполнена команда:

    certutil -v -csptest

    Во время выполнения команды запускался CryptoPro и запрашивал подключение носителя закрытых ключей.

    Такое поведение выглядело необычным и потребовало дополнительной проверки.

    Для просмотра зарегистрированных криптопровайдеров была выполнена команда:

    certutil -csplist

    В системе присутствовали CryptoPro CSP.

    Note

    На данном этапе не удалось установить, связана ли проблема непосредственно с CryptoPro.

    Было лишь зафиксировано, что криптографическая подсистема ведет себя нетипично и требует дальнейшей проверки.

    06. дополнительная диагностика

    Во время дальнейших попыток работы с ключами была получена ошибка:

    CertUtil: -delkey команда НЕ ВЫПОЛНЕНА

0x80090016

NTE_BAD_KEYSET

Набор ключей не существует

    Одновременно продолжали фиксироваться события:

    Schannel 36870

0x8009030D

    и

    RemoteConnectionManager 1057

Указан неправильный алгоритм

    К этому моменту можно было сделать несколько выводов.

    Что известно точно:

    • сеть исправна;
    • порт TCP/3389 исправен;
    • служба удаленных рабочих столов работает;
    • проблема связана с TLS-сертификатом либо его закрытым ключом.

    Что установить не удалось:

    • каким образом исходный сертификат оказался связан с используемым криптопровайдером;
    • когда именно возникла проблема;
    • что стало первопричиной повреждения конфигурации.

    07. создаем новый сертификат

    Восстанавливать существующий сертификат не стали.

    Было принято решение выпустить новый сертификат через штатный криптопровайдер Microsoft и привязать его к службе удаленных рабочих столов.

    Останавливаем службу RDP.

    Stop-Service TermService -Force

    Создаем новый сертификат.

    $Cert = New-SelfSignedCertificate `
    -DnsName $env:COMPUTERNAME `
    -CertStoreLocation "Cert:\LocalMachine\My" `
    -KeyAlgorithm RSA `
    -KeyLength 2048 `
    -HashAlgorithm SHA256 `
    -Provider "Microsoft Software Key Storage Provider" `
    -NotAfter (Get-Date).AddYears(5) `
    -TextExtension @(
        "2.5.29.37={text}1.3.6.1.5.5.7.3.1"
    )

$Hash = $Cert.Thumbprint

    08. привязываем сертификат к RDP

    Получаем объект RDP-Tcp.

    $ts = Get-CimInstance `
    -Namespace root/cimv2/TerminalServices `
    -ClassName Win32_TSGeneralSetting `
    -Filter "TerminalName='RDP-tcp'"

    Привязываем новый сертификат.

    Set-CimInstance `
    -InputObject $ts `
    -Property @{
        SSLCertificateSHA1Hash = $Hash
    }

    09. запускаем RDP

    Запускаем службу удаленных рабочих столов.

    Start-Service TermService

    Проверяем, что сертификат успешно привязан.

    Get-CimInstance `
    -Namespace root/cimv2/TerminalServices `
    -ClassName Win32_TSGeneralSetting `
    -Filter "TerminalName='RDP-tcp'" |
Select TerminalName, SSLCertificateSHA1Hash

    10. проверяем результат

    После выпуска нового сертификата:

    • RDP снова начал принимать подключения;
    • ошибка 0x4 исчезла;
    • события Schannel 36870 перестали появляться;
    • новые события RemoteConnectionManager 1057 больше не фиксировались.

    Никаких изменений в настройках сети, брандмауэра или NLA выполнять не потребовалось.

    вывод

    Если при доступном порте TCP/3389 клиент получает ошибку:

    Произошла внутренняя ошибка

Код ошибки: 0x4

    а в системном журнале одновременно присутствуют события:

    • Schannel 36870;
    • RemoteConnectionManager 1057,

    то проблему следует искать не только в службе удаленных рабочих столов, но и в криптографической подсистеме Windows.

    В данном случае после выпуска нового сертификата через Microsoft Software Key Storage Provider и его привязки к службе RDP проблема была полностью устранена.

    Что известно точно:

    • причиной отказа являлась невозможность использования TLS-сертификата или связанного с ним закрытого ключа;
    • выпуск нового сертификата полностью восстановил работу RDP.

    Что установить не удалось:

    • каким образом исходный сертификат оказался связан с используемым криптопровайдером;
    • что именно стало первопричиной повреждения конфигурации.
